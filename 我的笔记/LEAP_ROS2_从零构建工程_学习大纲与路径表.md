# LEAP ROS2：从空文件夹到完整机器人工程

> 学习大纲与阶段路径表｜编写日期：2026-11-01  
> 学习环境：Ubuntu 24.04＋ROS2 Jazzy；进入仿真阶段后加入 Gazebo Harmonic。  
> 最终硬件：自己已有的 ESP32-S3 三轮车。底盘具体结构、驱动和传感器留到硬件阶段核实。  
> 学习顺序：先在电脑上逐步搭建、理解软件工程，再阅读并构建固件，最后移植到实车。

## 阅读说明

这份大纲的目标，是带你从新建文件夹开始，经历一个机器人项目逐步形成的过程。每出现一个新需求，再引入解决这个需求的文件、程序或工具。

学习中始终回答四个问题：

1. 现在的小版本已经能做什么，还缺什么？
2. 为了补上这个能力，需要新增或修改哪些文件？
3. 新代码与已有模块怎样连接，数据从哪里来、到哪里去？
4. 怎样证明这一步真的完成了？

阶段顺序是为教学设计的，并非作者实际开发历史的还原。我们先构建便于理解的小版本，再逐步对照原项目。软件底盘、Gazebo 学习场景和部分实验程序是教学中额外补充的内容，不能说成原仓库已经提供的功能。

本文件是后续学习的指导性大纲，不是一次性执行脚本。阶段 0–1 提供可直接开始的操作；后续每个阶段再根据你的实际运行结果展开到逐文件、逐行代码讲解。文中的验收目标是建议的学习标准，尚未在你的电脑或实车上执行。

### 三种底盘要始终分清

| 形态 | 运行位置与作用 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| 理想软件底盘 | 电脑上的自编节点，根据速度计算位姿 | 话题、里程计、TF、基础运动学逻辑是否正确 | 真实电机性能、打滑、碰撞、硬件通信 |
| Gazebo 仿真底盘 | 电脑中的机器人模型、场景和仿真插件 | 运动、环境、传感器及上层建图导航能否形成闭环 | 实际轮速精度、供电能力、通信可靠性、真实传感器误差 |
| ESP32-S3 实车底盘 | 自己的控制板、电机、编码器和传感器 | 板级适配、电机控制、真实运动和整车功能 | 不能用一次成功演示代替重复验证 |

### 每个阶段怎么学

推荐按“理解需求 → 新增少量文件 → 运行观察 → 主动改一个变量 → 对照原项目 → 留下证据”的顺序推进。

- 先把本阶段最小版本做出来，再看对应的上游代码。
- 遇到 Python、C++、Linux 知识缺口，补到能理解当前代码即可。
- 每次只调整一个主要因素，例如速度、坐标系名称或参数值。
- 每个阶段保存启动命令、修改说明、输出结果和未解决问题。
- 验收通过后再进入下阶段；启动成功但不能解释数据流，不算完整通过。
- 没有通过的项目标记为“待补”，不把预期现象写成实测结果。

## 工程组织与命名

### 为什么拆成多个包

一个包承担一组相关职责，例如运动数据、模型资源、启动配置。一个包可以包含多个可执行程序；一个可执行程序也可以创建多个节点。入门时通常先按“一个程序创建一个节点”理解，后续再扩展。

模型包、接口包可以没有长期运行的业务节点。包名、程序入口名和运行时节点名也不必相同，排查时要区分。

### 逐步形成的目录

下表是最终组织方向，不要在第一天把所有空目录都创建出来。每个目录到对应阶段再出现。

| `src/leap_base/` | 3 | 理想软件底盘与后续需要的接口适配 |

## 阶段 0

**V0：从空文件夹建立工作空间**

### 需求与阶段边界

先给工程一个明确的位置，并弄清楚当前终端在哪个目录、后续代码放在哪里。这个阶段还没有机器人程序，完成目录创建不等于完成 ROS2 安装。

### 按顺序做

1. 打开自己的 Ubuntu 终端，执行 `pwd`，确认当前目录。
2. 创建工作空间、源码区和文档目录。
3. 检查 Jazzy 是否安装，以及 `colcon` 是否可用。
4. 创建第一份环境记录，写明实际检查结果。
5. 用文件管理器或 VSCode 打开工程，建立路径与界面的对应。

```bash
mkdir -p ~/leap_learning_ws/src
mkdir -p ~/leap_learning_ws/docs
cd ~/leap_learning_ws
pwd
ls
```

`~` 是自己的用户主目录，`mkdir -p` 创建目录，`cd` 切换位置。预期 `ls` 至少能看到 `src` 和 `docs`。

环境检查：

```bash
ls /opt/ros
command -v colcon
```

如果存在 `/opt/ros/jazzy/setup.bash`，再执行：

```bash
source /opt/ros/jazzy/setup.bash
printenv ROS_DISTRO
ros2 --help
```

预期发行版输出为 `jazzy`。如果未安装，就在 Ubuntu 24.04 上按 Jazzy 官方安装说明处理，不改装 Ubuntu 22.04。不要把 `source` 理解成安装命令。

### 新增文件与产出

- `docs/environment.md`：操作系统、ROS2 版本、Python 版本、工具是否可用。
- `docs/phase_00.md`：目录用途、执行过的命令、遇到的问题。
- 可选初始化 Git，先理解“记录一个可恢复版本”的用途，不急于上传远程仓库。

### 需要理解

- 文件夹、终端当前目录、绝对路径和相对路径。
- 工作空间是组织方式，不是另一个操作系统。
- `source` 修改当前 shell 环境；新终端是否生效取决于它加载了什么配置。
- 不要在同一个终端混合加载多个 ROS2 发行版来碰运气。

- [ ] 能说明 `src` 和 `docs` 各放什么。
- [ ] 已记录实际 ROS2 和构建工具状态。
- [ ] 进入阶段 1 前，`ROS_DISTRO` 为 `jazzy`，`ros2` 和 `colcon` 可用。

## 阶段 1

**V1：创建、构建并运行第一个功能包**

### 需求与阶段边界

理解一个程序怎样被包装成 ROS2 功能包，以及源码、安装结果、运行入口之间的关系。先使用 Python，减少同时学习编译语法的负担；之后对照 C++ 包。

### 按顺序做

1. 加载 Jazzy 环境，在 `src` 中创建 `leap_demo`。
2. 查看生成的每个主要文件，先阅读再构建。
3. 在工作空间根目录执行构建。
4. 新开运行终端，加载 Jazzy 与自己的工作空间。
5. 运行 `hello`，再修改输出内容、重新构建并观察变化。
6. 对照原项目的 Python `setup.py` 和 C++ `CMakeLists.txt`，识别两种包的入口写法。

```bash
source /opt/ros/jazzy/setup.bash
cd ~/leap_learning_ws/src
ros2 pkg create leap_demo \
  --build-type ament_python \
  --license Apache-2.0 \
  --node-name hello
cd ~/leap_learning_ws
colcon build --packages-select leap_demo
```

新开终端执行：

```bash
source /opt/ros/jazzy/setup.bash
source ~/leap_learning_ws/install/local_setup.bash
ros2 run leap_demo hello
```

预计输出 `Hi from leap_demo.` 后退出。这个自动生成的示例只是程序入口，不是已经持续参与通信的 ROS2 节点。

### 文件逐项认识

| 路径，相对于 `src/leap_demo/` | 本阶段需要理解的作用 |
| --- | --- |
| `package.xml` | 包的元信息、依赖和构建类型 |
| `setup.py` | 哪些 Python 代码和资源需要安装，运行入口对应哪个函数 |
| `setup.cfg` | 可执行入口的安装位置 |
| `resource/leap_demo` | ament 索引中的包标记 |
| `leap_demo/__init__.py` | Python 包标记 |
| `leap_demo/hello.py` | 实际执行的示例代码 |

构建后会出现 `build/`、`install/`、`log/`。修改自己的源文件，不要把生成目录当作主要编辑位置。

### 本阶段的小改动

把输出文字改成能识别的内容，例如 `LEAP learning V1`，重新构建并运行。再给程序入口换一个名字，检查 `setup.py` 与 `ros2 run` 是否同步变化。

理解 `entry_points` 中“入口名 = Python 模块路径:函数名”的含义。不要认为文件叫 `hello.py`，ROS2 就一定自动提供 `hello` 入口。

### 验收与证据

- [ ] 从新终端能运行自己的 `hello`。
- [ ] 能解释包名与程序入口名的区别。
- [ ] 修改输出内容后，运行结果确实变化。
- [ ] 能解释 `src/build/install/log` 的用途。
- [ ] 能指出 Python 包的安装入口，以及 C++ 包中构建、安装目标的位置。

产出：`leap_demo`、`docs/phase_01.md`、修改前后运行输出。

**常见问题：** 找不到包先检查是否加载工作空间；找不到可执行程序再检查入口注册和构建结果。不要一看到报错就重装 ROS2。

**下一阶段的需求：** 一个程序能运行了，现在让它持续工作，并与另一个程序交换速度数据。

## 阶段 2

**V2：建立真正的节点与第一条速度话题**

### 需求与阶段边界

把一次性输出程序改成持续运行的 ROS2 节点，再创建一个发布者和一个订阅者。本阶段只验证通信，不计算机器人运动。

### 新增与修改

- 修改 `hello.py`：引入 `rclpy`、节点和定时器。
- 新增 `cmd_publisher.py`：周期发布 `geometry_msgs/msg/Twist`。
- 新增 `cmd_listener.py`：订阅 `/cmd_vel` 并打印收到的字段。
- 修改 `package.xml`：声明实际用到的 `rclpy`、`geometry_msgs` 等依赖。
- 修改 `setup.py`：注册新增程序入口。

### 按顺序做

1. 逐行理解初始化、创建节点、进入事件处理、退出清理的过程。
2. 加入定时器，让节点每隔一段时间输出一次状态。
3. 创建速度发布者，先固定发送一个低速值。
4. 创建订阅者，打印 `linear.x` 和 `angular.z`。
5. 用命令行检查节点、话题、类型和频率。
6. 分别修改速度、发布频率、话题名，观察影响。
7. 停掉发布者，确认订阅端没有收到新数据；此时不讨论电机停车，因为还没有电机控制。

### 需要理解

- `Node`：节点对象；`spin()`：持续处理回调。
- 定时器回调和订阅回调分别什么时候执行。
- `Twist` 的线速度单位为 m/s，角速度单位为 rad/s。
- 差速学习模型先使用 `linear.x` 与 `angular.z`，侧向 `linear.y` 保持为 0。
- 同名话题不保证通信成功，还需要类型与 QoS 相容。
- 话题名 `/cmd_vel` 是我们采用的约定，不是 ROS2 自动执行运动的魔法命令。

### 观察工具

```bash
ros2 node list
ros2 topic list -t
ros2 topic info /cmd_vel --verbose
ros2 interface show geometry_msgs/msg/Twist
ros2 topic echo /cmd_vel
ros2 topic hz /cmd_vel
```

### 主动制造一次小故障

把接收端改成订阅另一个话题名。先预测结果，再用节点和话题信息定位问题，最后恢复。留下“现象—证据—原因—修复”的短记录。

### 验收与证据

- [ ] 能在节点列表看到自己创建的运行节点。
- [ ] 速度发送值和接收值对应。
- [ ] 改变频率后，能观察到相应变化。
- [ ] 能区分包、程序、节点、话题和消息类型。

## 阶段 3

**V3：建立理想软件底盘，输出里程计**

### 需求与阶段边界

创建 `leap_base`。它接收 `/cmd_vel`，维护当前位置和朝向，周期发布 `/odom`。此时的位置来自指令积分，并非编码器实测；在记录和展示中必须明确这一点。

### 新增文件

- `leap_base/mock_base.py`：订阅速度、更新位姿、发布里程计。
- 包声明和程序入口。
- `docs/interfaces.md`：开始记录话题、类型、单位、坐标系和数据来源。
- `docs/phase_03.md`：运动算例与实测输出。

### 按顺序做

1. 先只处理直行，保存目标线速度与当前位置。
2. 用定时器周期更新位置，使用实际经过的时间 `dt`。
3. 加入朝向角 `theta` 和角速度，处理平面转弯。
4. 把位置、朝向和速度填入 `nav_msgs/msg/Odometry`。
5. 设置正确的时间戳、父坐标系和子坐标系。
6. 增加速度限制、停止命令和指令超时逻辑。
7. 完成直行、原地转向、曲线、零速和断指令实验。

### 计算主线

初学时采用小步长积分：

```text
x_next     = x + v * cos(theta) * dt
y_next     = y + v * sin(theta) * dt
theta_next = theta + w * dt
```

这里 `x/y` 是固定坐标系中的位置，`v` 是车体前进方向的速度，`w` 是绕竖直轴的角速度。小步长积分存在数值误差；连续转弯测试的结果不要求与理想解析式逐位相同。

里程计的朝向使用四元数。绕 z 轴的平面旋转可以写为 `qz = sin(theta/2)`、`qw = cos(theta/2)`，其余两项为 0。不要用四个 0 表示初始朝向。

本教学工程约定里程计为 `odom → base_footprint`，车身及传感器的几何关系到阶段 4 再补齐。原项目可能使用不同的子坐标系名称，接入时通过接口表核对，不能只改一个名字就认为对齐。

### 建议验收用例

| 测试 | 输入 | 预期观察 |
| --- | --- | --- |
| 直行 | 持续输入 0.1 m/s，约 10 s | x 增量约 1 m，y 和朝向基本不变 |
| 原地转向 | v=0，w=0.5 rad/s，约 4 s | 朝向变化约 2 rad，位置基本不变 |
| 弧线运动 | v、w 同时非零 | 轨迹弯曲，转向方向与角速度符号一致 |
| 显式停止 | 持续发布零速度 | 位姿不再继续增长 |
| 指令超时 | 非零速度运行后停止发布 | 超时阈值加一个更新周期左右，内部目标归零 |

测试时间应使用记录的时间戳计算；手动按终端停止产生的误差需要注明。超时阈值先设为例如 0.5 s，作为学习参数。理想模型中停止很快，不代表实车物理停车也能达到同样时间。

### 验收与证据

- [ ] `/odom` 的位置和速度随输入变化。
- [ ] 直行、转向两个算例与预测相符，并记录误差来源。
- [ ] 时间戳持续更新，初始朝向合法。
- [ ] 停止发布非零指令后，位姿不会无限增长。
- [ ] 能解释“指令积分位置”与“编码器里程计”的区别。
- [ ] 接口表中写明数据来源、类型、单位和坐标系。

**常见问题：** 把定时器设为 20 ms 就永远用固定 `dt=0.02`；把角度当成弧度；将 `linear.x` 当作世界坐标 x 方向速度；只有日志变化却没有真正发布里程计。

**下一阶段的需求：** 有了位姿数字，要让模型显示出来，并把车身、轮子和传感器放在正确的位置。

## 阶段 4

**V4：加入模型、TF 和 RViz，看到机器人运动**

### 需求与阶段边界

先用简单几何形状构建自己的模型，再阅读原项目复杂模型。这个阶段的“动起来”来自阶段 3 的理想位姿，不是物理仿真。

- 新增 `rviz/display.rviz`。
- 给软件底盘加入 TF 发布，或单独写一个里程计到 TF 的转换节点，二选一。
- 配置模型资源的安装规则，确保安装目录能找到 URDF 和 RViz 文件。

### 按顺序做

1. 只定义车身 `base_link`，在 RViz 中看到一个方块。
2. 增加 `base_footprint` 与车身之间的固定关系。
3. 增加左右轮、支撑轮，以及雷达和 IMU 的安装坐标系。
4. 使用 `robot_state_publisher` 根据机器人描述发布部件关系。
5. 对活动关节提供对应 `joint_states`；演示轮子转动时区分人为演示值和真实轮速。
6. 连接 `odom → base_footprint` 动态变换，让整个模型随软件底盘移动。
7. 故意改错一个传感器坐标系或删除一条变换，练习观察和修复。

### 本阶段的坐标关系

| 父坐标系 | 子坐标系 | 谁负责提供 | 是否随运动改变 |
| --- | --- | --- | --- |
| `odom` | `base_footprint` | 软件底盘或唯一的里程计 TF 节点 | 是 |
| `base_footprint` | `base_link` | 机器人描述和 `robot_state_publisher` | 通常固定 |
| `base_link` | `laser_frame` | 机器人描述和 `robot_state_publisher` | 固定安装时不变 |
| `base_link` | `imu_link` | 机器人描述和 `robot_state_publisher` | 固定安装时不变 |
| `base_link` | 各轮子 link | 机器人描述＋活动关节状态 | 随关节状态变化 |

`map → odom` 到建图或定位阶段再引入，不要为了消除报错随便补一个固定变换。

### 需要理解

- URDF 描述结构，RViz 显示数据，TF 表达坐标系关系。
- `/odom` 消息不会自动变成 `/tf`，需要明确的发布者。
- `robot_state_publisher` 不会根据 `/cmd_vel` 自动移动机器人。
- 同一条 TF 只能有一个明确的权威发布者，不能让多个节点争抢。
- 模型尺寸以米为单位；显示外观与碰撞、惯量是不同内容。

### 验收与证据

- [ ] RViz 能显示模型，选定的 Fixed Frame 有合理依据。
- [ ] 直行、转向时模型运动与 `/odom` 一致。
- [ ] 修改雷达安装位置后，坐标显示随之变化。
- [ ] 能解释每条主要 TF 由谁提供。
- [ ] 能用 TF 检查工具定位一次缺失或命名错误。
- [ ] 未同时运行两个发布相同底盘动态 TF 的节点。

产出：模型文件、RViz 配置、运动截图或录屏、TF 责任表、`docs/phase_04.md`。

对照：原项目 `chuyun_description` 和 `chuyun_bringup.cpp`。注意其里程计、TF 实现的时间戳和初始化处理，理解后再决定复用，不能把所有现有写法都当成最佳实践。

## 阶段 6

**V6：建立 Gazebo 环境和传感器数据链路**

### 需求与阶段边界

用 Gazebo Harmonic 建立闭环仿真输入，替换阶段 3 的理想运动积分。该组合与 Jazzy、Ubuntu 24.04 配套；不沿用 Gazebo Classic 的插件教程直接套用。[参考 5]

### 新增文件

- 创建 `leap_sim`。
- `worlds/room.sdf`：简单房间、墙和少量障碍。
- 仿真模型配置：碰撞、惯量、轮子关节、驱动与传感器插件。
- `config/bridge.yaml`：Gazebo 与 ROS2 的消息桥接。
- `launch/sim.launch.py`：场景、机器人、桥接与显示启动组合。
- `docs/sim_data_flow.md`：话题方向、时间与 TF 来源。

### 分成六个小版本

1. **空场景：** 能启动世界，理解场景与机器人是不同资源。
2. **静态机器人：** 插入模型，检查尺寸、碰撞和重力下的稳定性。
3. **可运动机器人：** 接入差速驱动插件，确认左右轮关节与轮距、轮径。
4. **ROS2 控制：** 打通速度指令到 Gazebo 的路径，再获取里程计。
5. **雷达：** 加入雷达，打通 `/scan`，确认障碍物改变时读数变化。
6. **时间与记录：** 处理 `/clock`、`use_sim_time`，录制并回放一次实验；IMU 可随后补充。

### 切换时必须核对

| 内容 | 理想软件底盘模式 | Gazebo 模式 |
| --- | --- | --- |
| `/cmd_vel` 消费方 | 自己的 mock 节点 | 桥接与仿真驱动链路 |
| `/odom` 生产方 | 指令积分节点 | 仿真驱动或选定状态源 |
| 底盘动态 TF | mock 或转换节点 | 仿真侧或选定转换节点 |
| `/scan` | 没有真实场景数据 | 仿真雷达 |
| 时间来源 | 通常系统时间 | Gazebo `/clock` |

启动仿真后关闭 mock 底盘。不能让两套运动状态同时向上层发布。同理，Gazebo 和 ROS2 的 TF 发布链路需要选定，避免重复。

### 需要理解

- `visual`、`collision`、`inertial` 各自影响什么。
- Gazebo 消息与 ROS2 消息不是默认自动互通，桥接需要明确类型和方向。
- `LaserScan` 的角度、距离、时间戳、`frame_id` 和有效范围。
- 仿真时间暂停时，依赖仿真时间的节点行为也会受影响。
- 部分传感器采用 best-effort QoS；查看者需与发布者兼容。
- 录包回放可以复现数据，但没有可被控制的仿真底盘时，不能当成导航闭环。

### 验收与证据

- [ ] 发速度指令后，机器人在 Gazebo 世界中确实移动。
- [ ] 不是只有 RViz 模型或话题数值在变化。
- [ ] 雷达中的墙面方向和距离与场景对应。
- [ ] 改变障碍位置，雷达数据随之改变。
- [ ] `/odom`、TF 和 `/clock` 的责任来源明确。
- [ ] 必要节点使用一致的仿真时间。
- [ ] 录包停止源节点后，能回放所需数据；没有同时启动原 TF 数据源制造冲突。

产出：可复用仿真包、桥接表、场景截图、短录包、`docs/phase_06.md`。

**常见问题：** 模型穿地或抖动；传感器话题只存在于 Gazebo 一侧；雷达坐标系错误；仿真暂停却怀疑节点卡死；混用系统时间和仿真时间。

**下一阶段的需求：** 机器人已经能够运动和观察周围，现在把观察积累成地图。

### 需求与阶段边界

### 分步构建

1. **地图加载：** 先确认地图坐标、大小和显示正常。
2. **定位：** 设置初始位姿，观察雷达与地图的重合关系。
3. **代价地图：** 配置机器人轮廓或半径、障碍层和膨胀范围。
4. **路径规划：** 指定目标，观察全局路径是否可通行。

6. **完整任务：** 观察导航反馈、成功/失败状态与停止行为。
7. **异常场景：** 取消任务、加入障碍、发送不可达目标、暂停或中断关键数据。

### 四个必须核对的接口

| 接口 | 核对内容 |
| --- | --- |
| 速度指令 | 最终话题名、`Twist` 或 `TwistStamped` 类型、单位、是否经过限速/平滑节点 |
| 里程计 | 位姿和速度内容、时间戳、坐标系、是否使用融合结果 |
| TF | `map → odom → base_footprint → base_link → laser_frame` 是否连通且发布者唯一 |
| 雷达 | 角度和距离是否正确、时间是否新鲜、障碍是否进入代价地图 |

不同版本和配置可能采用不同的速度话题或消息类型。实际用 `ros2 topic list -t` 和 `ros2 topic info --verbose` 核实，再选择组件参数、重映射或适配节点。不要把名称相同当作类型已经匹配。

### 建议测试表

| 状态回传 | 编码器/传感器 → 测量与状态计算 → 状态队列 → 通信任务 → ROS2 消息 → 电脑端显示/定位/导航 |

不能只画一个“ROS2 → ESP32 → 电机”箭头就算读通。至少把一个命令值和一个反馈值追到字段和单位。

### 控制与单位算例

差速模型中，轮距为 `L`，车体线速度为 `v`，角速度为 `w`：

```text
左轮线速度 = v - w * L / 2
右轮线速度 = v + w * L / 2
轮角速度   = 轮线速度 / 轮半径
轮转速RPM  = 轮角速度 * 60 / (2*pi)
```

例如全部采用 SI 单位，`v=0.2 m/s`、`w=1 rad/s`、`L=0.18 m`，左右轮线速度应为 `0.11 m/s`、`0.29 m/s`。再与固件实际内部单位对照；原协议文档中存在 mm 与 m 的转换，不能直接照搬数值。

编码器部分要核实计数口径：电机轴还是轮轴、减速比、每转脉冲、倍频方式。名称中的 PPR/CPR 不能脱离具体驱动实现直接等同。

## 贯穿全程的接口与排错方法

### 接口表逐步维护

| 接口 | 建议记录字段 | 最早出现阶段 |
| --- | --- | --- |
| 速度指令 | 名称、类型、发布者、订阅者、单位、频率、超时 | 2 |
| 里程计 | 来源、位姿/速度字段、父子坐标系、时间戳、协方差含义 | 3 |
| TF | 父子关系、发布者、静态/动态、时间来源 | 4 |
| 雷达 | 类型、安装坐标系、角度与距离范围、频率、QoS | 6 |
| 地图 | 分辨率、原点、地图坐标系、保存与加载方式 | 7 |
| 导航任务 | Action/话题入口、反馈、结果、取消行为 | 8 |
| 服务 | 完整类型名、请求、响应、错误处理 | 9 |
| MCU 内部消息 | 字段、单位、队列长度、生产者、消费者 | 10 |

“同一个接口”意味着语义、类型与时间关系能对应。仅名称相同不够。

### 出问题时的检查顺序

1. **运行状态：** 进程是否启动，有没有清楚的报错？
2. **环境与构建：** 当前终端加载了哪个发行版和工作空间，运行的是哪份代码？
3. **节点与接口：** 节点是否存在，话题/服务类型是否正确？
4. **数据：** 是否真的有消息，字段、单位、频率是否合理？
5. **通信配置：** QoS 是否匹配，命名空间/重映射是否一致？
6. **坐标与时间：** TF 是否连通，发布者是否冲突，时间是否一致？
7. **业务逻辑：** 输入都正常后，再检查计算、状态机和参数效果。

硬件阶段额外先检查供电、接线和设备状态。不要在传感器根本没数据时直接调整导航算法参数。

### 常见症状速查

| 症状 | 优先检查 |
| --- | --- |
| `ros2 run` 找不到包 | 构建是否成功、是否加载正确工作空间 |
| 包存在但找不到程序 | 安装目标或 `entry_points`、可执行入口名 |
| 话题存在但接收不到 | 数据是否在发布、类型与 QoS、命名空间 |
| RViz 模型不动 | 动态 TF 是否变化、Fixed Frame、底盘是否更新 |
| 雷达位置明显偏移 | `frame_id`、安装 TF、角度方向和单位 |
| TF 显示旧数据或外推错误 | 时间戳、仿真时间设置、数据延迟与重复发布 |
| 导航有路径但不走 | 控制器输出、速度类型、桥接、底盘接收状态 |
| 模拟车正常而实车异常 | 单位、硬件限幅、控制周期、反馈符号、时延 |
| 改参数没有效果 | 修改了源码还是安装副本、加载哪个 YAML、是否支持动态更新 |

## 参考资料与使用顺序

先看当前阶段需要的那一小部分。仓库中的源码与配置用于对照工程实现；官方文档用于查工具和概念。作者飞书正文及 B 站视频未在本轮完整核读，因此本大纲不编造视频章节或学习时长。

1. [LEAP ROS2 主仓库](https://github.com/czu963889306-dev/leap_ros2)：硬件资料与软件仓库索引。
2. [ROS2 工作空间 chuyun_ws](https://github.com/czu963889306-dev/chuyun_ws)：原 `leap_ros_ws` 链接当前跳转目标；[本次参考快照](https://github.com/czu963889306-dev/chuyun_ws/tree/8043c442ee41c3beb62572502ae071a0ed75b238)。

4. [ROS2 Jazzy 官方教程](https://docs.ros.org/en/jazzy/Tutorials.html)：按环境、功能包、节点、话题、参数、launch、tf2 等主题查阅；[创建功能包的官方文档源文件](https://github.com/ros2/ros2_documentation/blob/jazzy/source/Tutorials/Beginner-Client-Libraries/Creating-Your-First-ROS2-Package.rst)。
